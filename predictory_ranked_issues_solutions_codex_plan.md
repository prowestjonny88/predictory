**Repo reviewed:** `prowestjonny88/predictory`

**Purpose:** Give the team a ranked, implementation-ready issue/solution plan, from most urgent to least urgent, with clear chart/display guidance and a master Codex prompt.

## 0. Current System Reality

The app has many strong pieces, but they do not yet behave like one clean decision-intelligence product.

### What the codebase currently contains

- Frontend sidebar currently exposes:
  - `/dashboard`
  - `/daily-planning`
  - `/forecast`
  - `/replenishment`
  - `/catalog`

- Additional pages exist but are currently not in the main sidebar:
  - `/prep-plan`
  - `/risk-center`
  - `/stock`
  - `/copilot`
  - `/scenario-planner`

- Backend currently includes:
  - weighted-blend fallback forecasting
  - model artifact loader
  - residual-band wrapper logic
  - cost-aware optimizer service
  - old safety-buffer prep engine
  - replenishment planner
  - copilot endpoints
  - forecast overrides
  - weather/holiday context
  - audit tables/events

- ML pipeline exists as a 12-step wrapper under `scripts/train_lightgbm.py` and `scripts/ml_pipeline/pipeline_common.py`.

### The main problem

The app has too many partially-overlapping truths:

```text
Offline ML pipeline says:
LightGBM + residual bands + optimized recommendations.

Live backend forecast says:
weighted_blend_fallback.

Planning router says:
forecast → prep plan → optimizer modification → top actions.

Copilot sometimes says:
explain numbers, but sometimes reconstructs uncertainty itself.

Frontend says:
backend data if available, demo fallback if not.

Product story says:
ML forecasts uncertainty, optimizer decides, Gemini explains/parses context.
```

The immediate revamp must make one product truth visible and defensible.

## P0-01 — Active forecast engine truth mismatch

### Issue

The product/pitch wants to imply:

```text
LightGBM powers forecast → uncertainty → prep optimization.
```

But the live backend forecast engine still builds forecasts using weighted recent totals, weekday pattern, moving average, and context adjustments. `run_forecast_for_date()` creates runs with:

```text
engine_name = "weighted_blend_fallback"
```

### Evidence

- `apps/api/forecasting/engine.py`
- `apps/api/services/model_loader.py`
- `scripts/ml_pipeline/pipeline_common.py`

### Why this is urgent

This is the highest-risk judging issue. If judges ask, “Is LightGBM actually generating this recommendation?”, the current answer is complicated.

### Solution

Separate and display two truths everywhere:

```text
1. Active forecast engine:
   What generated this forecast run?

2. Offline model artifact status:
   Is the trained LightGBM artifact available?
```

For now, if LightGBM is not wired into live backend inference, the UI must say:

```text
Active engine: weighted_blend_fallback
Offline model artifact: LightGBM available
```

Do not display:

```text
Active engine: LightGBM
```

unless backend forecast rows are actually produced by the LightGBM model.

### Implementation guidance

Update all model/engine badges to show both:

```text
Active forecast engine
Model artifact status
```

Avoid merging them into one “model status” phrase.

### Chart/display decision

Every chart that shows forecast values must show the active engine source in a small caption:

```text
Generated by: weighted_blend_fallback
```

or:

```text
Generated by: lightgbm_mlops_prototype
```

### Acceptance criteria

- Dashboard, Daily Planning, Forecast Evidence, and Model Evidence Drawer distinguish active engine from artifact status.
- No page says LightGBM generated the live forecast unless it actually did.
- If fallback is used, the UI says fallback clearly but professionally.

### Codex task

```text
Audit all frontend model/status badges and backend daily-plan response fields.
Add separate fields:
- active_engine_name
- model_artifact_status
- model_artifact_available
- forecast_source_label

Keep existing engine_name for backward compatibility if needed, but make UI labels truthful.
```

## P0-02 — p10/p50/p90 uncertainty source is inconsistent

### Issue

Daily Planning now expects backend `top_actions` to include p10/p50/p90, which is good. However, uncertainty is still reconstructed differently in multiple backend places.

Examples:

```text
planning/router.py:
uses residual bands or default fallback.

copilot/router.py:
_line_forecast_values() still derives:
p10 = p50 * 0.8
p90 = p50 * 1.25
```

### Evidence

- `apps/api/planning/router.py`
- `apps/api/copilot/router.py`
- `apps/web/src/lib/api/planning.ts`
- `apps/web/src/components/planning/UncertaintyBar.tsx`

### Why this is urgent

The same recommendation can show one demand range in Daily Planning and a different range in Gemini explanation or audit. That destroys trust.

### Solution

Create one canonical backend source for uncertainty:

```text
Forecast/Planning service computes p10/p50/p90 once.
Top actions store/return those values.
Copilot receives those same values.
Audit records those same values.
Frontend only renders them.
```

### Implementation guidance

Remove all independent p10/p90 multipliers outside the canonical uncertainty service.

The copilot should never call:

```text
p50 * 0.8
p50 * 1.25
```

for explanations.

### Chart/display decision

Use `UncertaintyBar` as the core Daily Planning visual.

Current `UncertaintyBar` already displays:

```text
Low
Expected
High
Recommended marker
```

But the values must come from the same backend evidence everywhere.

### Acceptance criteria

- Search result for `* 0.8` and `* 1.25` does not appear in copilot/planning uncertainty logic.
- Copilot explanation evidence p10/p50/p90 exactly matches RecommendationCard p10/p50/p90.
- Audit event p10/p50/p90 matches the selected recommendation values.
- Frontend never calculates uncertainty.

### Codex task

```text
Find every place p10/p90 is calculated.
Replace duplicated calculations with one shared backend helper.
Use this helper in:
- planning/router.py top_actions
- copilot/router.py explain-recommendation
- audit event creation
- manager-note apply flow

Do not change frontend API shape unless necessary.
```

## P0-03 — Old safety-buffer prep engine coexists with optimizer

### Issue

`apps/api/planning/prep.py` still implements the old prep formula:

```text
forecast + safety buffer - current stock
```

with waste-rate and freshness adjustments.

But the newer `apps/api/services/optimizer.py` calculates prep using:

```text
p10/p50/p90
unit price
unit cost
stockout cost
waste cost
critical ratio
batch size
```

### Evidence

- `apps/api/planning/prep.py`
- `apps/api/services/optimizer.py`
- `apps/api/planning/router.py`

### Why this is urgent

The product promise is “cost-aware decision intelligence,” but the code still has an older heuristic path. This creates confusion about which engine is the real one.

### Solution

Define one visible recommendation source:

```text
Final visible prep recommendation = optimizer output.
Old safety-buffer prep = fallback/baseline/debug only.
```

### Implementation guidance

The Daily Planning `top_actions` must always use optimizer-derived `recommended_prep`, `financial_exposure`, and `reason_summary`.

The old `generate_prep_plan()` path should not be used for the main demo unless explicitly labelled fallback.

### Chart/display decision

Do not use a generic prep trend chart here.

Use a decision breakdown:

```text
Low demand: 82
Expected demand: 100
High demand: 125
Opening stock: 5
Recommended prep: 105
Batch size: 5
```

### Acceptance criteria

- Daily Planning recommendation card values are optimizer outputs.
- `reason_summary` comes from optimizer logic.
- If old heuristic is used, UI says `fallback heuristic`.
- There is no ambiguous “recommended prep” coming from two different engines.

### Codex task

```text
Trace get_latest_daily_plan → _build_daily_plan_response → top_actions.
Ensure top_actions are generated only from optimizer-backed logic.
Keep legacy generate_prep_plan for backward compatibility but do not let it silently override optimizer decisions.
Add labels/metadata if fallback is used.
```

## P0-05 — Frontend/demo fallback can hide backend failure

### Issue

The frontend catches backend failures and returns demo data:

- `apps/web/src/lib/api/planning.ts`
- `apps/web/src/lib/api.ts`
- `apps/web/src/lib/demo-data.ts`

Daily Planning also locally mutates plan state for manager-note and audit fallback.

### Evidence

- `planningApi.latestPlan()` returns `demoLatestPlan()` on error.
- `api.dailyPlan()` catches and returns `demoDailyPlan()`.
- Daily Planning locally edits p10/p50/p90/recommended prep if backend apply fails.

### Why this is urgent

The demo can look fine even when backend is failing. This is good for demo survival but dangerous for development and truthfulness.

### Solution

Keep fallback, but make it impossible to miss.

Use:

```text
Source: backend
```

or:

```text
Source: demo fallback
```

Also distinguish:

```text
Backend source
Fallback source
Local-only optimistic update
```

### Implementation guidance

Any locally mutated fallback state should carry:

```text
data_source = "local_demo_mutation"
```

or a visible warning.

### Chart/display decision

Any chart using fallback/demo data must show a badge:

```text
Demo fallback data
```

### Acceptance criteria

- Backend failure cannot silently look identical to backend success.
- Manager note local fallback displays a warning.
- Audit fallback displays a warning.
- Demo fallback data is visually acceptable but clearly labelled.

### Codex task

```text
Audit all .catch(demo...) patterns.
Ensure every fallback response adds a visible source/status field.
Update UI badges for:
- backend
- demo_fallback
- local_demo_mutation
```
